# Billing Control v2 — история изменений

## 2026-07-28 — новая карточка приложения

- Раскрытая карточка полностью перестроена в вертикальный CRM-экран:
  приложение, периоды, единая таблица счетов и фотоотчёты.
- Все поля приложения редактируются одной формой: номер, юридическое лицо,
  содержание, сумма, даты отправки и подписания.
- Одна строка счёта содержит номер, сумму, срок оплаты, отметку оплаты,
  дату отгрузки и статус УПД.
- Отдельные интерфейсные блоки платежей и УПД, суммы и даты платежей,
  остатки, номер и даты УПД, содержание и период счёта удалены.
- Оплата хранится как ручной признак полного расчёта. 138 полностью
  оплаченных счетов перенесены автоматически, 61 счёт оставлен неоплаченным.
  138 старых строк платежей сохранены без изменений как архив.
- Добавлены статусы УПД `waiting`, `formed`, `sent`, `signed`. Все 199
  незаполненных УПД получили исходный статус `waiting`.
- После наступления даты отгрузки ожидающий УПД получает визуальное
  напоминание без автоматического изменения статуса.
- Фотоотчёты сохранили помесячную логику: ссылка встроена в месяц,
  просрочка мигает красным, `не требуется` показывается серым, текущий
  период остаётся базовым. Комментарии скрыты без удаления данных.
- Применены миграции `stage_6_application_card_redesign` и
  `stage_6_restrict_rls_event_function`; создание нового счёта и статуса
  УПД объединено миграцией `stage_6_atomic_invoice_creation`.
- Подтверждено: 199 счетов, 138 оплаченных, 61 неоплаченный, 199 УПД,
  0 пропусков, 0 дублей и 0 расхождений с архивными платежами.
- Пройдены 72 автоматических теста и транзакционная проверка функций
  сохранения.

## 2026-07-28 — УПД для всех счетов

- Подтверждено фактическое исходное состояние: заполненных УПД не было
  ни у одного счёта. 197 строк в `upds` являлись пустыми техническими
  заготовками, а у двух новых счетов заготовок ещё не было.
- Для всех 199 существующих счетов обеспечена одна доступная для заполнения
  запись УПД. Пропусков, дублей и заполненных вымышленными данными полей нет.
- Для каждого нового счёта строка УПД теперь создаётся автоматически
  серверным триггером.
- В редакторскую версию добавлен подраздел «УПД» для каждого счёта:
  номер УПД, сумма счёта, дата УПД, дата отправки и дата подписания.
- Сумма берётся из счёта и отдельно не редактируется. Дата УПД хранится как
  дата отгрузки связанного счёта и сохраняется с ручными полями одной
  серверной операцией.
- Режим `read` показывает УПД, но не формирует элементы редактирования и
  по-прежнему блокирует изменяющие запросы.
- Миграция применена к рабочей Supabase как
  `stage_5_invoice_upds_all_existing`.
- После миграции подтверждено соответствие: 199 счетов, 199 строк УПД,
  0 пропусков, 0 дублей, 0 заполненных УПД.
- Пройдены 63 автоматических теста.

- Форма счёта теперь всегда располагается в две строки по три поля, поэтому

- Исправленное продолжение номера счёта сохранено без изменений:
  `ОМ-13290/1 → ОМ-13290/2`.
- Схема и рабочие данные Supabase не изменялись.

## 2026-07-28 — номер нового счёта и календарь срока оплаты

  а не от номера приложения: после `ОМ-13290/1` предлагается
  `ОМ-13290/2`, даже если приложение имеет номер `395`.

- Для разделённых счетов `base_invoice_no` сохраняется без числового

- Сетка редактора счёта больше не выходит за правую границу финансового
  блока; полям дат гарантирована ширина для текста и кнопки календаря.
- На более узких экранах поля редактора располагаются в две строки по три.
- Схема и рабочие данные Supabase не изменялись.

### Состояния фотоотчётов

- Полный URL больше не показывается в обычном виде: ссылка встроена в название
  месяца фотоотчёта.

  и мигает. Для пользователей с настройкой уменьшения движения мигание

  календарного месяца фотоотчёта.

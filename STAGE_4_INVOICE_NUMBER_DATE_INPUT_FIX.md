# Billing Control v2 — номер нового счёта и поле срока оплаты

Дата: 28 июля 2026 года.

## Исправленные ошибки

### Номер нового счёта

- Предложенный номер больше не строится из номера приложения.
- Серия определяется по уже существующим счетам конкретного приложения.
- После счёта `ОМ-13290/1` форма предлагает `ОМ-13290/2`, даже если номер
  приложения — `395`.
- Используется максимальный числовой суффикс выбранной серии.
- Если существующий счёт ещё не имеет суффикса, он считается первым и для
  следующего предлагается `/2`.
- При отсутствии счетов поле номера остаётся пустым: программа не подменяет
  неизвестный номер счёта номером приложения.
- Поле остаётся редактируемым до сохранения.

### Базовый номер

- Для `ОМ-13290/1`, `ОМ-13290/2` и последующих строк в
  `base_invoice_no` сохраняется `ОМ-13290`.
- Это правило применяется при создании и редактировании счёта.
- Произвольные нечисловые окончания после `/` не отбрасываются.

### Календарь срока оплаты

- Элементы формы счёта теперь могут корректно сжиматься внутри финансовой
  панели без выхода сетки за её правую границу.
- Для всех трёх полей даты задана достаточная минимальная ширина.
- На более узких экранах шесть полей формы переходят в две строки по три
  поля, поэтому календарь срока оплаты остаётся внутри поля.

## Supabase

- Схема и рабочие строки не изменялись.
- Контрольный запрос только на чтение подтвердил исходный сценарий:
  приложение `395`, счёт `ОМ-13290/1`, пустой срок оплаты.
- При следующем сохранении этого счёта приложение приведёт
  `base_invoice_no` к `ОМ-13290`.

## Проверка

- Сценарий `ОМ-13290/1 → ОМ-13290/2` закреплён отдельным тестом.
- Проверены пустой список счетов, ненумерованный первый счёт, несколько
  суффиксов и выбор последней серии.
- Проверено формирование базового номера при создании счёта.
- Проверены ограничения ширины полей даты и адаптивная сетка формы.
- Пройдены 54 unit-теста.
- Синтаксис и грамматика Python 3.10 проверены.
